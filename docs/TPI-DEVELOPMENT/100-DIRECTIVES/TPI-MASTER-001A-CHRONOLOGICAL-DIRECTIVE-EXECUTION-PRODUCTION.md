====================================================================

DIRECTIVE TPI-MASTER-001A
CHRONOLOGICAL DIRECTIVE EXECUTION — PRODUCTION WEBSITE

PRIORITY: HIGH

theparanormalinitiative

====================================================================
1. PRIMARY OBJECTIVE
====================================================================

Continue TPI-MASTER-001.

The previous execution repaired a StudioFlow dropdown issue but did
not fulfill the primary mission.

The mission is to process ALL historical TPI directives, beginning
with the oldest and continuing to the newest, implementing their
applicable requirements into the EXISTING PRODUCTION WEBSITE.

The historical directives are the requirements authority.

The existing production website repository is the implementation
target.

The separate StudioFlow development website is NOT the implementation
target and must not be used to reconstruct production.

Do not start another unrelated StudioFlow repair.

====================================================================
2. ESTABLISH THE COMPLETE CHRONOLOGICAL REGISTER
====================================================================

Locate and review:

- The unified TPI master directive archive.
- The existing Master Directive Register.
- Original historical conversations and directive documents.
- The production website directive index.
- Existing implementation and completion reports.
- Subsequent corrections, replacements, and amendments.

Reconcile all available directive sources into one chronological
execution register.

Each directive must include:

- Original directive identifier.
- Original date and time, where available.
- Original source document or conversation.
- Original requirements.
- Subsequent amendments.
- Superseding directives, if applicable.
- Current production implementation status.
- Required corrective work.
- Verification evidence.
- Deployment version, where applicable.

Do not invent missing dates or timestamps.

Where chronological timestamps cannot be established, preserve
documented source order and identify the uncertainty.

Do not assume the existing register is complete without checking
the original historical sources.

====================================================================
3. EXECUTE DIRECTIVES OLDEST TO NEWEST
====================================================================

Identify the earliest historical directive that has not been
fully reconciled against the current production website.

Begin with that directive.

For EACH directive:

STEP 1:
Read the complete original instructions.

STEP 2:
Identify later corrections, amendments, or superseding requirements.

STEP 3:
Inspect the relevant existing production website code.

STEP 4:
Determine whether the directive is:

- Already implemented and verified.
- Implemented but not verified.
- Partially implemented.
- Not implemented.
- Superseded.
- Blocked.

STEP 5:
If the functionality already exists and works correctly,
preserve it.

STEP 6:
If partially implemented, complete or repair the missing
requirements.

STEP 7:
If missing, implement the applicable requirements directly
into the production website repository.

STEP 8:
Run appropriate tests and regression checks.

STEP 9:
Deploy reviewed, non-destructive changes using the existing
controlled Cloudflare deployment process.

STEP 10:
Verify the actual production website behavior.

STEP 11:
Record the results in the Master Directive Register.

STEP 12:
Proceed to the next historical directive.

Continue sequentially.

Do not select work based on whichever problem is most recently
visible unless that work is required by the directive currently
being processed or is necessary to protect production.

====================================================================
4. PRODUCTION WEBSITE IS THE IMPLEMENTATION TARGET
====================================================================

All implementation work must target the existing production
website repository.

Inspect the actual deployed production code and assets when
necessary to establish what is currently running.

Do not assume the repository and deployed Worker are identical.

Do not rebuild StudioFlow from the separate development project.

Do not copy the development website into production.

Do not modify the separate StudioFlow development application.

Use the original historical directives to determine the required
behavior of the production application.

Preserve existing working features.

====================================================================
5. SUPERSEDED DIRECTIVES
====================================================================

Some historical directives were corrected or replaced by later
instructions.

Do not restore obsolete functionality simply because an earlier
directive requested it.

For each superseded requirement:

- Identify the original directive.
- Identify the replacement directive.
- Record the relationship.
- Preserve the latest applicable approved requirement.
- Mark the obsolete requirement SUPERSEDED.

Continue processing directives chronologically while respecting
the final approved requirements.

====================================================================
6. PRODUCTION DATA AND FUNCTIONALITY PROTECTION
====================================================================

Preserve:

- Crossroads of the Unknown.
- TPI Acceptance Test A.
- TPI Acceptance Test B.
- Existing studio configurations.
- Browser-local studio data.
- Existing media and recordings.
- Authentication and authorization.
- Administration functionality.
- Community functionality.
- Live Bridge functionality.
- Existing Cloudflare D1 and R2 data.
- Unrelated production website functionality.

DO NOT:

- Reset production databases.
- Delete owner data.
- Replay database migrations blindly.
- Overwrite existing studios.
- Remove existing recordings or media.
- Start public broadcasts during testing.
- Deploy unrelated working-tree changes.
- Replace the entire production application.
- Perform destructive operations without explicit approval.

Before deploying, review the changed-file manifest and verify
that the changes are limited to the intended directive.

====================================================================
7. VERIFICATION REQUIREMENTS
====================================================================

A directive is not complete simply because its code exists.

Verify the actual production functionality whenever possible.

Use:

- Production source inspection.
- Deployed asset inspection.
- Automated tests.
- Authenticated API verification.
- Browser interaction.
- Persistence verification.
- Cloudflare deployment confirmation.
- Regression testing.

If browser automation fails, distinguish automation failure
from application failure.

Use alternative verification methods where appropriate.

Do not falsely claim that an authenticated user interaction
was verified when only an API or source-code test passed.

Record unresolved verification limitations accurately.

====================================================================
8. MASTER EXECUTION REGISTER
====================================================================

Maintain a continuously updated register containing:

DIRECTIVE ID

SOURCE
ORIGINAL REQUIREMENT
SUPERSEDING DIRECTIVE
PRODUCTION IMPLEMENTATION STATUS
FILES MODIFIED

REMAINING WORK

Permitted statuses:

VERIFIED COMPLETE
IMPLEMENTED — VERIFICATION PENDING
PARTIALLY COMPLETE
NOT IMPLEMENTED
SUPERSEDED
BLOCKED

Every historical directive must be accounted for.

Do not mark a directive VERIFIED COMPLETE without sufficient
supporting evidence.

====================================================================
9. CONTINUATION POLICY
====================================================================

This is a sequential implementation program, not a single
investigation.

Do not stop after producing an audit or status report.

Continue through the historical directive sequence as long as
the next action is authorized, technically feasible, and safe.

If a directive is blocked:

1. Document the precise blocker.
2. Record what has already been completed.
3. Identify the action required to resolve the blocker.
4. Continue to the next independent directive.

If a directive requires destructive changes, unavailable
credentials, or additional owner authorization, do not perform
those actions without approval.

Do not use an unrelated blocked directive as a reason to halt
the entire implementation program.

The next report must identify the actual earliest historical
directive processed.

Do not substitute a recent StudioFlow repair for the earliest
directive in the chronological archive.

====================================================================
11. COMPLETION CRITERIA
====================================================================

TPI-MASTER-001A is complete only when:

1. All available historical directive sources have been
   reconciled into the master register.

2. Every directive has been accounted for in chronological
   order.

3. All applicable requirements have been inspected against
   the existing production website.

4. Missing or incomplete requirements have been implemented
   or accurately documented as blocked.

5. Completed functionality has been verified against the
   actual production website.

6. Superseded requirements have been documented correctly.

7. Existing production data and functionality have been
   preserved.

8. The master register accurately reflects the final
   production implementation state.

====================================================================
FINAL INSTRUCTION
====================================================================

STOP TREATING EACH NEW STUDIOFLOW PROBLEM AS A SEPARATE
DEVELOPMENT PROJECT.

FOLLOW THE COMPLETE HISTORICAL DIRECTIVE REGISTER.

START WITH THE OLDEST DIRECTIVE.

INSPECT THE EXISTING LIVE WEBSITE IMPLEMENTATION.

VERIFY WHAT ALREADY WORKS.

IMPLEMENT WHAT IS MISSING.

REPAIR WHAT IS BROKEN.

DEPLOY AND VERIFY SAFELY.

DOCUMENT THE RESULT.

MOVE TO THE NEXT DIRECTIVE.

CONTINUE UNTIL EVERY APPLICABLE HISTORICAL DIRECTIVE HAS
BEEN ACCOUNTED FOR.

THE EXISTING LIVE PARANORMAL INITIATIVE WEBSITE IS THE
IMPLEMENTATION TARGET.

THE ORIGINAL DIRECTIVES ARE THE REQUIREMENTS AUTHORITY.

NO MORE COMPETING DEVELOPMENT IMPLEMENTATIONS.

====================================================================
END DIRECTIVE TPI-MASTER-001A
