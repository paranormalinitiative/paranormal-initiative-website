=====================================================================
1. OBJECTIVE
=====================================================================

Implement reliable, automatic cache-busting for StudioFlow's
local development JavaScript and CSS assets.

PROBLEM:

Codex modifies StudioFlow source files, but Opera sometimes
continues displaying an older version of the application.

TPI-040A introduced no-store cache headers, but the owner
continues encountering apparent stale-interface behavior.

GOAL:

Ensure local browsers automatically request the latest
StudioFlow JavaScript and CSS whenever those files change.

Do not require the owner to:

- Clear browser caches.
- Clear website data.
- Delete cookies.
- Delete IndexedDB.
- Perform repeated hard refreshes.
- Change browser origins.

=====================================================================
2. INVESTIGATE EXISTING ASSET LOADING
=====================================================================

Inspect:

studio/index.html

studio/assets/index-j2x9m9vI.js

studio/assets/index-DXjilBOR.css

worker.js

wrangler.local.toml

Determine:

1. How StudioFlow HTML references JavaScript and CSS.
2. How the local Worker serves those assets.
3. Whether query parameters are preserved during routing.
4. Whether HTML is being cached.
5. Whether asset responses use no-store headers.
6. Whether the current asset names are generated by a build tool.
7. Whether existing development tooling already supports
   asset fingerprinting or versioning.

Do not assume caching is the confirmed cause of the
Room Bridge layout defect.

=====================================================================
3. IMPLEMENT AUTOMATIC CACHE-BUSTING
=====================================================================

Use a deterministic asset version.

PREFERRED APPROACH:

Generate a version identifier from the actual asset contents
or the existing build manifest.

Example:

index-j2x9m9vI.js?v=<content-version>

index-DXjilBOR.css?v=<content-version>

REQUIREMENTS:

- Version changes when asset contents change.
- Version remains stable when contents are unchanged.
- No random version on every request.
- No unnecessary asset duplication.
- No new storage system.
- No external service.
- No Cloudflare requests.
- No production behavior changes.

If existing hashed filenames already provide reliable
fingerprinting, determine whether correcting their update
process is preferable to adding query parameters.

Choose the smallest maintainable solution.

=====================================================================
4. LOCAL WORKER INTEGRATION
=====================================================================

Ensure the local Worker serves versioned assets correctly.

Requirements:

1. Existing authentication remains enforced.
2. Query parameters do not bypass access controls.
3. Asset routing continues working.
4. Correct MIME types are returned.
5. JavaScript modules continue loading.
6. CSS continues loading.
7. Existing no-store behavior remains intact.
8. Production caching behavior remains unchanged.

Do not weaken Creator Studio authentication.

=====================================================================
5. AUTOMATIC UPDATE BEHAVIOR
=====================================================================

When Codex modifies StudioFlow's JavaScript or CSS:

1. The local asset version must change.
2. The local HTML must reference the current version.
3. Opera must request the updated asset.
4. Safari must request the updated asset.
5. Chrome must request the updated asset.

Do not require manual version-number editing after each change.

Do not require restarting unrelated development services.

If the Worker needs a controlled local restart, use the
existing service-management mechanism.

Do not create another background process.
